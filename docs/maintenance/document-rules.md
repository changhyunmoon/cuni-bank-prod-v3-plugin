# 외부 분석 자료를 문서에 반영하는 기준

> 범위: 플러그인 docs 유지보수 | 성격: 사용자 요청에 따른 작성 지침

사용자·팀원이 제공한 분석에서 이후 개발 판단에 필요한 정보만 추려 뼈대·케이스·reference 중 알맞은 문서에 반영한다.

1. 저장소 경계, 책임, 실행 조건, 컨벤션, 데이터 계약, 반복되는 제약을 우선 추출한다.
2. 현재 코드로 확인할 수 있는 버전·경로·포트·테스트·설정은 대조한다. 환경별 차이는 적용 범위를 표시한다.
3. 명시된 업무 지침, 코드 관찰, 제공된 운영 정보, 제안을 구분한다. 관찰만으로 팀 지침을 덮어쓰지 않는다.
4. [docs 라우터](../README.md)에서 관련 문서를 먼저 선택한다. 본문을 확인한 뒤 갱신·연결하고, 새로운 질문에 답할 때만 파일을 추가한다.
5. 근거 파일·확인 날짜·관련 저장소 기준을 남긴다. 문서 추가·이동·삭제·책임 변경 시 라우터 트리거 표와 스킬·에이전트·문서의 참조 링크를 같은 작업에서 갱신한다.

- 전달받은 원문 전체, 대화 이력, 일회성 로그, 비밀값은 복사하지 않는다.
- 확인할 수 없는 정보는 '제공 정보·미검증'으로 표시한다. 코드와 충돌하면 현재 상태와 차이를 짧게 기록한다.
- 경로는 원칙적으로 저장소 기준 상대 경로를 쓴다. 환경별 절대 경로는 예시·현재 확인 경로로 구분한다.
- 문서 하나는 질문 하나에 답한다. 본문 30~60줄 목표, 80줄 초과 시 분리를 검토하며 짧은 내용을 억지로 늘리지 않는다.
- 작성 양식은 [문서 템플릿](../../templates/docs/)을 사용한다. 스킬·에이전트에는 적용 조건과 원문 링크만 연결한다.
- 라우터에는 실제 존재하는 문서의 경로와 트리거만 기록한다. 예정 문서나 본문 전체를 넣지 않는다.
- 라우터에 없는 주제만 추가 검색한다. 연결 후에는 링크 대상의 존재와 트리거 표의 누락을 확인한다.
- 확인 결과를 전달할 때는 기록한 위치와 중요한 수정·미확인 사항을 알린다.
- 첫 문장에 문서의 답을 적고, 본문은 역할 → 처리 순서 → 개발 시 확인할 점으로 구성한다.
- 긴 약어·필드 나열보다 쉬운 설명과 짧은 표를 사용한다. 인증·인가처럼 혼동되는 개념은 먼저 풀어 쓴다.
- '전부·항상·유일' 같은 단정은 전체 범위를 검증했을 때만 쓴다. 기존 구현과 새로 따라야 할 규칙을 구분한다.

## 어느 폴더에 둘까

| 폴더 | 넣는 문서 | 판단 질문 | 양식 |
|---|---|---|---|
| `foundation/` | 모든 작업의 전제가 되는 구조·경계·공통 규칙 | 어떤 기능을 만들든 알아야 하는가 | reference·convention·guide |
| `cases/<영역>/` | 특정 기능·상황에서만 따르는 절차·규칙·체크리스트 | "이럴 때"로 시작하는 트리거를 쓸 수 있는가 | [case](../../templates/docs/case.md) |
| `reference/` | 여러 케이스가 공유하는 계약·지도·흐름 | 두 개 이상의 케이스가 같은 내용을 필요로 하는가 | reference·flow |
| `maintenance/` | 문서 작성·검증 기준 | 문서 관리자만 필요한가 | — |

- 케이스 문서는 공통 계약을 복사하지 않고 reference로 링크한다. 케이스에만 해당하는 규칙만 본문에 둔다.
- 새 케이스를 만들면 맨 위에 `언제 읽나 / 읽지 않는 경우`를 쓰고 라우터 트리거 표에 행을 추가한다.

- 관련: [docs 라우터](../README.md), [소스 기준](source-baseline.md).
