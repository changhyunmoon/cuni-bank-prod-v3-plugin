# 기존 화면과 일관성 맞추기

> 범위: Admin·User 화면 시안(prototype)과 실제 템플릿 | 상태: 사용자 결정 반영 | 근거: CUNI-536 데이터 모니터링 시안 수정 이력(v1~v5.9, 최종 설계안, 2026-10-14)
>
> 언제 읽나: 화면 시안을 만들거나 고칠 때, 화면 구현을 마치고 검토할 때, 사용자가 화면 수정 의견을 줄 때 | 읽지 않는 경우: 화면 없이 API·DB만 바꿀 때

새 화면의 모든 요소는 기존 화면에서 같은 역할을 하는 요소를 **복사**해 만든다. 어디서 복사했는지 기록하고, 모양이 어긋나면 CSS를 더하지 말고 표준 요소로 바꾼다.

## 반복된 원인

CUNI-536 시안은 같은 종류의 수정을 열 번 넘게 반복했다. 원인은 다섯 가지다.

| 원인 | 실제 사례 | 막는 규칙 |
|---|---|---|
| 요소를 직접 만들었다 | 검색 라벨 `<span>`, 새 클래스(`period-range` 등), 기간 사용 여부 select, `btn-type1` 동작 버튼 | 작성 순서 2·3 |
| 어긋난 모양을 CSS로 덮었다 | 자체 모달과 하단 버튼 넘침 보정, 새 요소마다 `.dark` 색 추가, 빈 `head_optionLeft`로 오른쪽 정렬, 입력 폭 180→150px 축소 | 작성 순서 4 |
| 요청에 없는 기능·기본값을 넣었다 | 마스킹·강제 마스킹·자동 동기화, 기본 기간 7일, 전체 결과 엑셀 1,000건 제한, 프로토타입 전용 `?theme=` | 작성 순서 1 |
| 비교 기준 없이 소스만 봤다 | 참고 화면을 task → ipstatus → vmManager 순서로 바꿈, 한 테마만 확인, 팝업 입력칸이 다크에서 흰 칸 | 작성 순서 1·5 |
| 수정 의견을 한 곳만 고쳤다 | 메인 검색 줄 라벨을 지운 뒤에도 팝업 검색 줄은 다른 구조로 남아 다시 고침 | 수정 의견 반영 |

## 작성 순서

1. **범위와 기준 정하기**: 요청한 검색·열·버튼·동작만 만든다. 요청에 없는 기능, 기본값(기본 기간 등), 제한은 넣지 않고 "제안"으로 묻는다. 같은 모듈에서 검색 줄·버튼·표 구성이 가장 비슷한 **디자인 기준 화면**을 1~2개 골라 사용자에게 확인받는다.
2. **요소별 근거 표**: 만들 요소(검색 줄, 기간, select, 동작 버튼, 표, 팝업, 팝업 안 검색·입력, 빈 결과·알림)마다 복사할 근거를 정해 진행 기록에 표로 남긴다.

   | 요소 | 근거(파일:줄) | 바꾼 것 |
   |---|---|---|
   | 검색 줄 | `monitoring/vmManagerManagement/list.html:514-560` | select 옵션, id |

   근거는 [컴포넌트 표준](../../reference/ui-components.md) → 디자인 기준 화면 → [참고 화면](../../reference/screen-references.md) → 같은 모듈 기존 화면 순서로 찾는다. 근거가 없는 요소는 만들기 전에 사용자에게 제안해 확정한다.
3. **그대로 복사**: 근거의 구조·클래스·인라인 style을 그대로 옮기고 id·문구·옵션만 바꾼다. 근거 화면에만 있는 화면별 클래스와 각 문서의 "복사하지 않는다" 항목은 빼고 옮긴다.
4. **어긋나면 CSS 대신 요소를 바꾼다**: 모양이 다르거나 테마 색이 맞지 않으면, 근거와 다른 마크업·위치를 썼다는 뜻이다. `<style>`·인라인 style·`.dark` 규칙을 더하지 말고 근거를 다시 찾는다. 같은 클래스라도 위치(메인·팝업, `tbl-type2`·`tbl-type4`)에 따라 모양이 다르다([테마](../../reference/theme.md)). 한 줄에 안 들어가도 폭을 줄이지 말고 사용자와 정한다.
5. **실제 화면과 비교**: 기준 화면과 근거 화면을 로컬 서버에서 열어 같은 창 크기, 다크·화이트 두 테마로 나란히 비교한다(방법: [prototype-screen](../../../skills/prototype-screen/SKILL.md)의 실제 화면 비교). 팝업은 iframe 안 요소의 계산된 색까지 본다.

## 수정 의견 반영

- 의견을 규칙 한 줄로 바꾼다(예: "라벨을 지워라" → "검색 영역에는 라벨을 두지 않는다").
- 그 규칙으로 메인·팝업·두 테마 전체에서 같은 패턴을 찾아 함께 고친다. 지적받은 한 곳만 고치지 않는다.
- 진행 기록에 `의견 → 규칙 → 고친 위치`를 남긴다.
- 다른 화면에도 적용될 결정이면 시안 승인 뒤 [update-docs](../../../skills/update-docs/SKILL.md)로 컴포넌트 표준 등에 "확정, 사용자 결정 날짜"로 반영하자고 제안한다.

## 점검표

시안 제출 전과 구현 완료 후 모두 확인한다. 검토 에이전트도 이 표를 쓴다.

- [ ] 요청 범위 밖 기능·기본값·제한·안내 영역·전용 토글이 없다.
- [ ] 디자인 기준 화면을 사용자와 정했고, 요소별 근거 표에 빈칸이 없다.
- [ ] 검색 줄: 한 줄, 라벨 없음, 대상 → 기간 → 검색 조건 → 검색어 → 검색 버튼, `~`가 보이게 `head_optionLeft`에 `font-size: 14px`([목록 배치](list-screen.md#검색-줄-구성-admin)).
- [ ] 동작 버튼: 같은 줄 오른쪽, `btn-type5`, 내보내기 맨 끝, 문구는 자료사전 값. 긴 문구는 `width: auto; margin-right: 15px`.
- [ ] 기간: 요구사항에서 정한 A/B 한 방식([기간 검색](period-search.md)), 기간 사용 여부 select 없음.
- [ ] 버튼 비활성 모양 없음. 할 수 없는 동작은 `$.alert`.
- [ ] 표: 공통 grid 옵션 그대로, 긴 열·가로 스크롤 처리는 사용자와 정한 방식.
- [ ] 팝업: 별도 문서(iframe)·`popup_layout`·`showPopup` 크기(너비 1000 이상), 자체 모달 없음, 우상단 × 없이 하단 닫기·취소, 하단 버튼과 본문 겹침 없음.
- [ ] 팝업 안 검색은 `head_option` 검색 줄, 긴 값은 `tbl-type4 vertical` textarea(`tbl-type2` 안 입력칸은 다크에서 흰 칸).
- [ ] 새 클래스·화면 모양용 `<style>`·직접 지정한 색 없음. 쓴 class가 모두 모듈 CSS나 표준에 있다.
- [ ] 선택 목록·코드 표시는 코드사전·자료사전 값(시안은 `코드사전:`·`자료사전:` 표시, 구현은 조회 함수).
- [ ] Admin은 다크로 시작, 다크·화이트 두 테마에서 실제 화면과 비교한 기록이 있다.
- [ ] 받은 수정 의견마다 같은 패턴을 화면 전체에서 고친 기록이 있다.
