# 작업 결과와 승인 기록

실행 산출물은 플러그인이 아닌 대상 업무 프로젝트에 저장한다. 프로젝트의 기존 실행 결과 관리 문서·규칙을 우선 적용한다. 규칙이 없으면 업무 루트의 `outputs/<YYYYMMDD-feature-slug>/`를 사용한다. 날짜·이름 충돌 시 식별자를 추가하고 기존 작업을 덮어쓰지 않는다. 여러 모듈 작업은 한 결과 폴더에 모듈 경로를 기록한다.

필요 단계에서만 다음 파일을 만든다.

```text
progress.md
requirements.md
implementation-plan.md
prototype.html               화면 배치·디자인 확인용 한 파일
verification.md
evidence/
  snapshots/                 승인·실행·리뷰 기준별 JSON
  runs/                      실행 명령과 원본 로그·보고서
```

플러그인에 작업 산출물·스크린샷·승인 내용을 저장하지 않는다. 비밀값이나 세션 정보를 기록하지 않는다.

## progress.md 필수 정보

- 작업 ID, 업무 루트, 대상 모듈, 원 요청 요약, 결과 폴더.
- 실행 모드: full-feature / standalone-prototype / skill-evaluation. [공통 검증 계약](verification.md)의 모드별 기준을 따른다.
- 현재 단계: requirements / prototype / design / implementation / verification / done.
- 상태: working / awaiting-approval / needs-input / verification-incomplete / complete.
- 요구사항·시안·설계의 버전, 현재 승인 여부, 문서 링크.
- 승인 이력: 대상·버전, 사용자 응답의 짧은 인용/요약, 날짜, 대화 식별정보가 있으면 참조, 승인 범위.
- 적용 문서와 소스 기준, 변경된 가정·결정, 남은 일, 다음 행동, 실행 제약.

## 전이 규칙

| 현재 산출물 | 다음 단계 조건 |
|---|---|
| 요구사항 | 해당 버전의 사용자 승인 → 시안 |
| 시안 | 해당 버전의 사용자 승인 → 구현 설계 |
| 구현 설계 | 해당 버전의 사용자 승인 → 업무 구현 |
| 구현 | 독립 검토·실행 검증 및 수정 → 검증 결과 확정 |

실제 사용자 응답을 근거로 승인 상태를 갱신한다. 침묵, 도구 성공, 에이전트 의견, 부분 수정 요청을 전체 승인으로 해석하지 않는다. 기존 대화에서 명확하게 승인된 내용은 기록하고 재요청하지 않는다. 승인 범위가 불명확한 경우 해당 부분만 확인한다.

의미 있는 내용 변경 시 버전을 올리고 변경 요약을 남긴다. 업무 범위·사용 흐름·계약 변경은 해당 승인과 영향받는 후속 승인을 무효화한다. 오탈자·승인된 범위의 오류 수정은 승인 유지 이유를 기록한다. 사용자가 명시적으로 단계 생략·변경을 지시하면 지시와 검증 제한을 기록하고 따른다.

중대한 변경의 예: 신규/변경 API 계약, 화면 이동·흐름 변경, DB 스키마·트랜잭션 경계 변경, 권한·데이터 접근 범위 변경. 범위 내 수정의 예: 오탈자·라벨 문구 수정, 이미 합의된 범위 안에서의 버그 수정, 승인된 화면 구조를 바꾸지 않는 스타일 조정. 경계가 불명확하면 범위 내 수정으로 단정하지 말고 사용자에게 확인한다.

재개 시 progress와 승인 대상 문서, 현재 소스 변경을 대조한다. 파일의 승인 문구만으로 신뢰하지 말고 기록된 사용자 승인 근거를 확인한다. 변경이나 근거가 불명확하면 필요한 부분만 사용자에게 확인한다.

## 승인·검증 대상 고정

승인 요청을 제출하기 직전에 대상 문서·`prototype.html`의 파일 목록과 SHA-256을 snapshot으로 보관한다. 외부 자산은 원본 경로·버전 또는 해시도 기록한다. 사용자 승인 응답은 이 snapshot ID에 연결하며, 승인 이후 내용을 바꾼 snapshot으로 과거 승인을 덮어쓰지 않는다. 해시는 대상의 동일성 증거이며 사용자 승인 자체를 증명하지 않는다.

[evidence_snapshot.py](../scripts/evidence_snapshot.py)를 사용한다. 아래 경로는 실제 절대 경로로 치환하고 출력은 업무 프로젝트에 둔다.

```text
python <plugin>/skills/develop-screen-feature/scripts/evidence_snapshot.py record --root <business-root> --files <file1> <file2> --output <output>/evidence/snapshots/<id>.json
python <plugin>/skills/develop-screen-feature/scripts/evidence_snapshot.py verify --snapshot <output>/evidence/snapshots/<id>.json
```

실행 전·후에도 입력 소스·설정·fixture 목록을 고정하고 모듈별 Git 루트, HEAD 커밋, dirty 상태와 변경 파일 해시를 저장한다. 업무 루트는 컨테이너이므로 단일 HEAD를 가정하지 않는다. untracked 파일, 삭제·이름 변경, 검증에 쓰인 미커밋 변경을 포함한다. 로그·보고서는 별도 실행 결과 snapshot으로 고정한다. 비밀값은 증거에 복사하지 않고 필요한 경우 해시 또는 비밀이 아닌 설정 식별자만 남긴다.

실행 전·후 입력 기준이 달라지면 검증 결과를 그 상태의 통과 증거로 사용하지 않는다. 완료·재개·리뷰 제출 전에 verify하고 불일치/파일 누락은 `stale`로 표시한다. 파일 목록 밖 새 관련 파일도 변경 목록 비교로 확인한다. 영향 분석 후 해당 테스트·리뷰를 재실행한다. 영향 없는 변경이면 제외 근거와 새 기준을 기록하고 이전 결과를 무조건 전체 통과로 재사용하지 않는다.

승인 대상의 차이가 오탈자 등 범위 내 수정이면 이전·현재 snapshot과 승인 유지 근거를 남긴다. 기능·흐름·계약이 바뀌면 앞의 전이 규칙대로 해당 승인과 영향받는 후속 승인을 무효화한다. 도구를 실행할 수 없다면 동일 정보를 수동 기록하고 검증 제한을 명시하며 snapshot 확인을 수행했다고 보고하지 않는다.
