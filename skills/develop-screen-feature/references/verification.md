# 독립 에이전트 검증

이 절차는 메인이 제출한 실행 증거(로그·보고서·스크린샷)를 리뷰어가 대조·재검토하는 정합성
검토다. snapshot은 증거가 제출 이후 몰래 바뀌지 않았음을 보장할 뿐, 그 증거가 실제 실행에서
나왔는지 자체를 원천 보증하는 완전 독립 실행검증은 아니다. 메인 Claude는 통합·수정·빌드·테스트·브라우저 실행 검증을 맡는다. Claude Code의 Agent 도구로 아래 등록된 서브에이전트에 독립 검토를 위임한다. 세 에이전트는 Read·Grep·Glob만 사용하는 읽기 전용이며 셸 실행이나 코드/승인 파일 쓰기를 하지 않는다. 실행 증거를 검토하고 필요한 테스트를 메인에게 요청한다. 사용 가능한 동시 실행 수에 맞춰 병렬 또는 순차 실행한다.

| 역할 | 확인할 근거와 내용 |
|---|---|
| 요구사항·화면 | 승인 요구사항·시안, 요구사항별 구현, 화면 상태·흐름, mock 잔존 여부 |
| 개발 표준 | docs 라우터의 케이스 트리거 표에서 관련 케이스를 직접 선택, 기존 참고 소스, 레이아웃·공통 함수·Proxy·표시값 규칙 |
| 백엔드·연동 | 승인 API 계약과 실제 코드, 권한·데이터 범위·입력 검증·DB 접근·예외·트랜잭션 |

## Claude Code 호출

플러그인 이름은 `.claude-plugin/plugin.json`의 `cuni-bank-v3-prod-plugin-v3`다. Agent 도구의 `subagent_type`에는 아래 플러그인 범위 이름을 사용한다. 런타임에 노출된 이름과 대조하고 이름을 찾을 수 없으면 로딩 문제를 보고한다.

- `cuni-bank-v3-prod-plugin-v3:screen-reviewer` — [에이전트 정의](../../../agents/screen-reviewer.md)
- `cuni-bank-v3-prod-plugin-v3:convention-reviewer` — [에이전트 정의](../../../agents/convention-reviewer.md)
- `cuni-bank-v3-prod-plugin-v3:backend-reviewer` — [에이전트 정의](../../../agents/backend-reviewer.md)

| 시점 | 호출 대상 |
|---|---|
| 시안 제출 전 | 기본 호출하지 않음(사용자가 프로토타입을 직접 확인). 사용자가 요청하면 screen-reviewer |
| 구현 설계 제출 전 | convention-reviewer, backend-reviewer |
| 최종 구현 후 | 세 에이전트 모두 |
| 피드백 수정 후 | 수정의 영향을 받는 역할만 재검토 |

시안 스킬이 같은 버전으로 수행한 검토를 메인 스킬에서 반복하지 않는다. 자동 선택에만 기대지 말고 해당 단계에서 명시적으로 위임한다. 검증 에이전트에 전체 개발 스킬을 미리 주입하거나 승인·수정을 맡기지 않는다.

## 위임 입력

서브에이전트가 부모 대화·스킬 내용을 이미 안다고 가정하지 않는다. 다음 입력을 위임 프롬프트에 포함한다.

```text
실행 모드: full-feature / standalone-prototype / skill-evaluation
검토 단계: prototype / design / implementation / recheck
플러그인 루트와 docs/README.md 절대 경로:
공통 검증 계약 파일의 절대 경로:
업무 루트, 대상 모듈, 적용 CLAUDE.md 및 규칙 경로:
작업 결과 폴더, 요구사항/시안/설계의 경로와 버전·승인 상태:
검토할 파일 목록과 변경 전 기준(해당하는 경우):
선택한 케이스 문서와 적용 기록, 입력 snapshot ID·경로, 모듈별 HEAD·dirty 기준:
실행 근거 파일(명령·보고서·스크린샷), 실행 제약:
검토 범위, 재검토라면 이전 발견 사항과 수정 파일:
```

필수 경로·대상 버전이 없거나 자료에 접근할 수 없으면 메인에게 보완을 요청한다. 시안 제출 전에는 시안이 아직 미승인이고 설계 제출 전에는 설계가 미승인임을 정상으로 취급한다. 에이전트가 승인 상태를 바꾸지 않는다.

### 모드별 기준

- `full-feature`: 승인된 요구사항 ID를 기준으로 진행한다. 승인 요청 전 검토 중인 해당 산출물은 미승인인 것이 정상이다.
- `standalone-prototype`: 사용자 원 요청과 정리한 범위·가정·관찰 가능한 완료 조건을 기준으로 검토한다. 필요하면 임시 요구사항 ID를 부여하되 승인 이력을 만들지 않는다. 승인된 요구사항 문서나 백엔드 설계가 없다는 사실을 결함으로 보고하지 않는다.
- `skill-evaluation`: 지정된 평가 요청·입력·허용 범위와 기대 관찰을 기준으로 스킬을 시험한다. 대표 화면 시안 시험에는 실제 사용자 승인이나 업무 코드 구현을 요구하지 않는다. 평가 성공을 제품 개발 승인 또는 실제 서버 연동 성공으로 기록하지 않는다.

모든 모드에서 [케이스 선택·기록 규칙](doc-coverage.md)에 따라 케이스 문서 선택의 누락도 검토한다. snapshot 검증은 메인이 실행하며 읽기 전용 리뷰어는 결과와 파일을 대조한다. stale 증거를 현재 코드의 통과 근거로 받아들이지 않는다.

## 반환 형식

1. 단계·검토 대상 버전과 읽은 문서/소스 목록.
2. 검토 결론: 수정 필요 / 검토 범위 내 발견 사항 없음 / 근거 부족. 사용자 승인 여부와 구분한다.
3. 발견 사항: `ID | 상태 | 심각도 | 요구사항 ID | 파일·줄 | 문서 규칙/재현 근거 | 영향 | 수정 제안 | 재검증 방법 | 대상 snapshot`.
4. 요구사항 또는 담당 검토 항목별 `통과 / 실패 / 미실행`과 근거. 코드 검토 통과와 실제 동작 통과를 구분한다.
5. 미검증 영역, 메인에게 필요한 추가 실행·자료, 남은 질문.

심각도는 P1(필수 동작·권한·데이터 무결성 문제), P2(기능·표준 위반), P3(선택적 개선)로 구분하고 근거 없이 높이지 않는다. 발견 사항을 억지로 만들지 않는다. 문서와 코드의 충돌·추측·확인된 결함을 구분한다.

각 에이전트에 업무 루트, 변경 파일/차이, 승인 산출물 버전, docs 라우터 경로, 실행 제약을 전달한다. 메인의 결론을 정답으로 제공하지 않는다. 에이전트는 관련 원문과 코드를 직접 확인하고 `심각도 | 파일·위치 | 재현 조건/근거 | 영향 | 수정 제안`으로 결과를 보고한다. 발견 사항 없음과 미검증 영역을 구분한다.

빌드·테스트는 [빌드](../../../docs/foundation/build-and-run.md)·[테스트](../../../docs/foundation/testing.md) 기준을 따른다. 실제 실행 명령·작업 디렉터리·종료 결과·테스트 건수·skip과 보고서 경로를 남긴다. 테스트 0건, NO-SOURCE, 코드 열람은 실행 통과가 아니다. 화면은 가능한 경우 서버에서 실제 Thymeleaf 렌더링과 사용자 흐름을 확인한다. 정적 시안 성공은 서버 연동 성공의 근거가 아니다.

메인은 발견 사항별 반영/미반영과 근거를 업무 프로젝트의 verification.md에 기록하고 수정·재검증한다. 중대한 잔여 결함이 있으면 전체 완료 처리하지 않는다. 승인 범위를 바꾸는 수정은 해당 단계로 되돌린다. 필요한 재검증만 하고 새 근거 없는 반복 실행은 피한다. 환경·권한·의존성 때문에 실행 불가하면 원인과 필요한 조건을 기록한다.

## 실행 증거와 피드백 종료

1. 리뷰어가 요구사항별 정상·예외 시나리오와 관찰할 결과를 제안한다. 관련되면 권한 없음, 다른 프로젝트 데이터 접근, 빈 결과, 잘못된 입력, API 실패를 포함하고 해당 없는 항목은 이유를 남긴다.
2. 메인이 실행 전 입력 snapshot을 고정하고 필요한 테스트·브라우저 검증을 실행한다. 원본 명령·작업 경로·환경 식별자·종료 코드·로그·보고서·스크린샷을 업무 결과 폴더에 저장한다. 민감값은 수집 단계에서 제외하거나 마스킹하며 원본 증거라는 이유로 노출하지 않는다.
3. 실행 후 입력 동일성을 확인하고 결과 파일도 snapshot으로 고정한다. 리뷰어는 원본 증거로 기대 결과 충족을 재검토한다. 요약이나 스크린샷 하나로 수행하지 않은 API·권한 검증까지 통과시키지 않는다.
4. 수정 후에는 영향받는 코드 검토·실행 검증을 stale로 표시하고 새 증거로 해당 리뷰어의 재검토를 받는다.

발견 사항 ID는 재검토에도 유지하고 다음 상태 중 하나로 관리한다.

| 상태 | 의미와 전이 조건 |
|---|---|
| 미처리 | 근거와 영향을 기록했으며 해결 전 |
| 수정 | 변경 위치·snapshot을 기록했으나 재검증 전 |
| 재검증 완료 | 해당 관찰 조건을 새 증거로 확인, 리뷰어 재검토 완료 |
| 근거기각 | 반증하는 요구사항·원문·실행 근거와 판정 이유 기록 |
| 사용자결정 | 승인 범위·업무 규칙 충돌을 명시하고 결정 요청 |
| 환경차단 | 필요한 환경·권한·자료와 미검증 영향을 기록 |

다수결이나 구현자의 선호로 기각하지 않는다. 사용자 요구사항·적용 문서의 범위·실제 소스와 실행 증거를 대조한다. 의견이 충돌하면 양쪽 근거와 적용 조건을 정리하고, 범위 안 기술 문제는 메인이 근거로 해결하며 업무 결정은 사용자에게 요청한다.

같은 발견 사항이 수정·재검토 2회 후에도 동일 원인으로 남거나 새 코드·증거 없이 같은 의견만 반복되면 그 항목의 재호출을 중단한다. 원인·시도·남은 선택지를 기록하고 사용자결정 또는 환경차단 조건에 해당하면 그 상태로 둔다. 단순 미해결 버그는 미처리로 유지하고 다른 진단 방법을 선택한다. 독립적으로 진행 가능한 항목은 계속 처리한다. 반복 제한을 결함 무시나 전체 완료의 근거로 쓰지 않는다.

전체 완료에는 필수 완료 조건의 현재 증거, 필수 리뷰 수행, P1/P2의 재검증 완료 또는 근거기각이 필요하다. P3 선택적 개선은 미반영 이유와 잔여 영향을 공개할 수 있다. 필수 실행 항목이 사용자결정·환경차단·미실행이면 구현 완료와 검증 미완료를 분리한다.

에이전트 도구가 없으면 같은 관점으로 자체 검토하되 독립 검증 미실시를 표시한다. 에이전트 검증을 수행한 것처럼 보고하지 않는다. 최종 결과는 요구사항별 `통과 / 실패 / 미실행`과 코드 검토·빌드·실제 동작의 검증 수준을 구분한다.
