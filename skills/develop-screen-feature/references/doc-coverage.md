# 케이스 문서 선택과 적용 기록

문서 선택 매핑은 [docs 라우터](../../../docs/README.md)에만 있다. 이 파일은 라우터에서 고른 문서를 **언제 다시 확인하고 어떻게 기록하는지**만 정한다. 규칙 본문을 대체하지 않는다.

## 선택

1. 요구사항을 정리한 직후 라우터의 케이스 트리거 표에서 해당하는 행을 **모두** 고른다. 예를 들어 "목록 화면 + 엑셀 + 새 API"는 list-screen, table-setup, excel-export, cmp-new-api, db 케이스에 해당한다.
2. 각 케이스 문서 맨 위의 `언제 읽나 / 읽지 않는 경우`로 적용 여부를 판정한다. 비슷한 다른 케이스로 안내되면 그 문서로 바꾼다.
3. 케이스 문서가 링크한 reference는 필요한 내용이 있을 때만 연다.
4. 요구사항이나 설계가 바뀌면 트리거 표를 다시 대조해 케이스를 추가하거나 제외한다.

## 확인 시점

| 문서 영역 | 확인 시점 |
|---|---|
| `foundation/`(project-map, coding-rules, 대상 모듈 구조), 업무 CLAUDE.md와 적용 규칙 | 시작·재개 |
| `cases/screen/`, 대상 모듈 frontend reference | 요구사항·시안·구현 |
| `cases/table/` (엑셀 포함) | 요구사항·시안·설계·구현·검증 |
| `cases/display-value/` | 시안·설계·구현, 완료 시 등록 안내 |
| `cases/backend/`, `cases/db/`, `reference/data-access.md` | 설계·구현·검증 |
| `foundation/build-and-run.md`, `foundation/testing.md` | 설계·검증 |

## 기록

각 산출물(`requirements.md`·`implementation-plan.md`·`verification.md`)에 다음 표를 남긴다.

`케이스 문서 | 적용/해당 없음/확인 불가 | 참고 소스 경로 | 적용 내용 또는 사유 | 미해결 차이`

- 해당 없음은 기능 범위 근거를 적는다. 확인 불가는 파일 부재·접근 불가 등 원인과 영향을 적는다.
- 읽기만 하고 적용 확인을 통과로 표시하지 않는다. 케이스 문서의 검증 항목은 verification.md에서 항목별로 결과를 남긴다.
- User 작업에 Admin 예제가 적용 가능한지는 User 실제 코드로 대조한다.

개발 표준 리뷰어는 메인의 선택 목록을 답으로 받아들이지 않는다. 요구사항과 변경 파일을 보고 라우터에서 케이스를 독립적으로 다시 고르고, 누락이나 부당한 "해당 없음" 판정을 지적한다. 문서와 코드가 충돌하면 명시된 기준, 적용 범위, 현재 코드 근거를 함께 제시한다.
