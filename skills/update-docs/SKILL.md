# docs 반영

Claude Code 플러그인 스킬이다. `/cuni-bank-v3-prod-plugin-v3:update-docs`로 호출하거나 docs 반영 요청에 적용한다. 아래 상대 링크는 이 SKILL.md 위치 기준이며, 서브에이전트에는 0단계에서 확인한 절대 경로를 전달한다. 메인 대화에서 승인 상태를 유지하고 전체 진행을 서브에이전트에 넘기지 않는다.

## 작업 원칙

1. **승인 전 수정 금지.** 반영 계획 표를 승인받기 전에는 docs를 수정하지 않는다. 승인한 항목만 적용한다.
2. **지침은 사용자만 정한다.** 사용자가 명시적으로 "표준·지침으로 하라"고 한 항목만 지침으로 쓴다. 코드 패턴은 사용 빈도와 무관하게 관찰, 추론한 개선안은 제안, 확인하지 못한 정보는 제공정보·미검증이다.
3. **충돌은 보고만 한다.** 기존 문서와 다른 정보는 계획 표에서 보고하고 사용자가 고른 대로만 반영한다.
4. **업무 소스는 읽기만 한다.** 업무 루트의 코드·설정·DB를 수정하지 않는다. 커밋은 사용자가 요청할 때 플러그인 저장소에서만 한다.
5. 기준은 [문서 반영 기준](../../docs/maintenance/document-rules.md)이다. 배치 판단표·작성 원칙을 이 스킬에 복사하지 않고 그 문서를 따른다.

## 0. 루트 판별

```bash
node <이 스킬>/scripts/resolve_roots.mjs [--business-root <업무 루트>] [--plugin-root <플러그인 클론>]
```

| mode | 상황 | 진행 |
|---|---|---|
| `A` | 플러그인 클론에서 `claude --plugin-dir .`로 실행 | `plugin_root`의 docs를 수정한다. 코드 추출이면 업무 루트를 물어 `--business-root`로 다시 실행한다 |
| `B` | 업무 루트에서 `--plugin-dir <클론>`으로 실행 | `plugin_root`의 docs를 수정하고 `business_root`의 코드를 읽는다 |
| `plan-only` | 마켓플레이스 설치 캐시에서 실행 | 플러그인 클론 경로를 묻는다. 받으면 `--plugin-root`로 다시 실행하고, 없으면 5단계 계획 표까지만 제시한다 |

- `plugin_git.dirty`가 true면 반영 전부터 있던 docs 변경임을 사용자에게 알리고, 이번 작업 변경과 구분한다.
- 결과 JSON의 `repos`(HEAD·branch·dirty)는 6단계 소스 기준 기록에 쓴다.

## 1. 입력 판별

| 입력 | 예 | 추출 절차 |
|---|---|---|
| 텍스트 | 붙여넣은 문서, 파일 경로, 회의 정리 | [텍스트 추출](references/extract-text.md) |
| 코드 | `cmp:<경로>`의 조회 방식을 컨벤션으로 정리 | [코드 추출](references/extract-code.md) |
| 혼합 | 설명 문서 + 관련 코드 경로 | 텍스트 추출 후 코드로 대조 |

코드 입력의 범위(저장소·경로·정리할 기능)가 불분명하면 탐색 전에 한 번 묻는다. 지침으로 삼으라는 명시적 지시가 있었는지 이 단계에서 기록한다.

## 2. 기준 로드

[docs 라우터](../../docs/README.md), [문서 반영 기준](../../docs/maintenance/document-rules.md), [문서 템플릿](../../templates/docs/)만 읽는다. 나머지 문서는 4단계에서 후보로 고른 것만 연다.

## 3. 추출

입력별 절차로 **지식 항목**을 만든다. 형식은 두 입력 모두 같다.

`ID | 내용 | 성격(지침/관찰/제안/제공정보·미검증) | 근거(저장소:상대 경로 또는 출처) | 적용 범위 | 답하는 질문`

- 원문 전체, 대화 이력, 일회성 로그, 비밀값, 개인 절대 경로는 항목으로 만들지 않고 제외 목록에 사유와 함께 남긴다.
- **긴 입력은 위임한다.** 텍스트가 약 300줄을 넘거나 코드 범위가 여러 디렉터리·20개 파일 이상이면 `cuni-bank-v3-prod-plugin-v3:doc-extractor`([정의](../../agents/doc-extractor.md))에 나눠 맡긴다. 텍스트는 제목 단위, 코드는 저장소·계층 단위로 나누고 독립적인 조각은 병렬로 위임한다. 위임 입력은 [에이전트 정의](../../agents/doc-extractor.md)의 형식을 따른다.
- 서브에이전트 결과는 메인이 병합한다. 같은 내용은 하나로 합치고 근거를 모은다. 조각끼리 다르면 둘 다 남기고 차이를 표시한다.

## 4. 배치

항목마다 둘 곳을 정한다.

1. 라우터에서 같은 질문에 답하는 기존 문서를 찾아 본문을 읽는다. 있으면 해당 섹션 **갱신**이다.
2. 기존 문서와 내용이 다르면 **충돌**로 분류한다. 덮어쓰지 않는다.
3. 맞는 문서가 없으면 [문서 반영 기준](../../docs/maintenance/document-rules.md)의 폴더 판단표로 폴더를 정하고 해당 템플릿으로 **신규** 문서를 계획한다. 여러 케이스가 공유하는 계약은 reference에 두고 케이스에서는 링크만 건다.
4. 새 문서·이동이 생기면 라우터 트리거 표와 이를 참조하는 스킬·에이전트 링크 변경도 계획에 넣는다.

## 5. 반영 계획 승인

[승인 형식](references/approval-format.md)대로 반영 계획 표, 충돌 표, 제외 목록을 제시하고 **반영 승인**을 요청한다. 대기 중에는 조사만 한다. 사용자가 항목별로 제외·성격 변경·대상 변경·충돌 선택을 지시하면 표를 고쳐 다시 제시한다. `plan-only`이면 여기서 끝내고 클론에서 다시 실행하는 방법을 알린다.

## 6. 적용

승인된 항목만 적용한다.

- 기존 문서는 해당 섹션만 고친다. 문서 형식(범위·상태·근거 머리말, 지침/관찰/제안 표)을 유지한다.
- 신규 문서는 템플릿 주석의 규칙을 따르고 주석은 지운다. 본문 30~60줄 목표, 80줄을 넘기면 분리를 사용자에게 알린다.
- 라우터·스킬·에이전트 링크를 같은 작업에서 갱신한다.
- 코드에서 추출했으면 [소스 기준](../../docs/maintenance/source-baseline.md)에 `## <YYYY-MM-DD> <주제>` 섹션을 추가한다: 확인 범위, 0단계의 저장소 HEAD·작업 트리 상태, 검색·확인한 것과 실행하지 않은 것.
- 텍스트에서 확인하지 못한 정보는 본문에 '제공 정보·미검증'으로 표시한다.

## 7. 검증과 보고

```bash
node <이 스킬>/scripts/check_docs.mjs --plugin-root <plugin_root> [--files <이번에 바꾼 docs 경로...>]
```

- `errors`(링크 깨짐·라우터 미등록 케이스)는 고친 뒤 다시 실행한다. `warnings`(80줄 초과·비밀값 의심)는 해당 줄을 확인하고 보고에 포함한다.
- 보고: 변경 문서와 바뀐 섹션, 반영 항목 수와 성격별 분포, 반영하지 않은 항목(제외·충돌 유지), 미검증 사항, 검사 결과. 커밋은 요청이 있을 때만 한다.
